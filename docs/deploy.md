# Deploying on Render

Two ways. Both build the repo-root `Dockerfile`.

## A. Blueprint (one step, recommended)
Dashboard -> **New** -> **Blueprint** -> pick the GitHub repo. Render reads `render.yaml`, creates the web service and a
Postgres database, and asks you once for the three secrets (`RPC_URL`, `ATTRIBUTION_KEY_B58`, `KEEPER_PAYER_B58`).

## B. By hand (what the screen offers)
| Card on "Create a new Service" | Use it for |
|---|---|
| **Web Services** | the API (public URL, `/healthz`) - required |
| **Postgres** | the database - required |
| **Background Workers** | only if you run the keeper as its own service (not needed: it can run inside the API) |
| Static Sites | the UI later (or host the UI on Vercel) |
| Private Services, Cron Jobs, Key Value, Workflow | not needed |

Web Service settings: Language **Docker**, Dockerfile Path `./Dockerfile`, Health Check Path `/healthz`, Region Frankfurt
(same region as the database so the internal connection string works), plan **Free** (works, with the sleep trade-off below) or the paid always-on plan.

## Environment variables
| Variable | Value |
|---|---|
| `DATABASE_URL` | the database's **Internal** connection string |
| `RPC_URL` | your Helius/other RPC URL for the cluster |
| `PROGRAM_ID` | `AC6AtoRALLszNGNLmHte2UXKzCqBYQKhPdtq5qs77nkL` (devnet) |
| `CLUSTER` | `devnet` (<= 8 chars; must equal the cluster tag in the campaigns) |
| `ATTRIBUTION_KEY_B58` | claim-signing secret key (base58). Fresh per cluster |
| `TRUST_PROXY` | `1` (Render sits in front: use X-Forwarded-For for rate-limit IPs) |
| `TRUSTED_PROXY_HOPS` | `3` (default, correct for Render, which sits behind Cloudflare: a request arrives as `client, Cloudflare edge, Render internal proxy`; observed on 2026-10-29). How many proxy entries sit in front of the service. The client address is that many entries from the RIGHT of `X-Forwarded-For`; entries to the left are client-controlled and ignored. Verify with `curl -H 'X-Forwarded-For: 1.2.3.4' <api>/v1/whoami`: `ip` must be YOUR address (compare with `curl https://api.ipify.org`), not `1.2.3.4` and not a private `10.x` address: a private address means the setting is too low and EVERY visitor shares one rate-limit bucket. Recheck after any change of hosting or CDN |
| `MINT` + `KEEPER_PAYER_B58` | set BOTH to run the settlement keeper inside the API process |
| optional | `CLAIM_TTL_SECS`, `MAX_PRICE_BASE_UNITS`, `LIMIT_PER_*_PER_MIN`, `KEEPER_TICK_SECONDS` |

Render turns env vars into Docker build args too; the Dockerfile never references any of them, so no secret enters an image layer.

## Costs and limits (from Render's docs; verify current prices yourself)
- Free web services **spin down after 15 min idle and take ~1 min to wake**. Workable for development and a demo if you ping `/healthz` every ~10 min (an external uptime monitor); free hours (750/month) are shared across the whole workspace.
- While asleep the embedded keeper does not run. The merchant gateway settles right after delivery, so the main flow is unaffected; the keeper catches up on wake.
- The CDP key (`CDP_API_KEY_ID/SECRET`) is NOT needed on this service: it never calls the facilitator. It belongs to the merchant gateway service.
- Free Postgres: 1 GB, **expires 30 days after creation** (+14-day grace), no backups. Fine through the hackathon; upgrade or recreate after.
- Background workers have **no free tier**: another reason to embed the keeper.

## Key hygiene
- A fresh attribution key per cluster. The devnet test keys in `spike/keys/` must never be used on mainnet.
- The keeper payer only pays fees/rent and can settle only after the hold; it cannot refund. Keep a small SOL float.
- A KMS/HSM signer can replace `LocalKeySigner` (the `ClaimSigner` interface) without touching callers.

## Verified locally
`docker build -t noux-api:local .` and run with the env above: `/healthz` answers and the process runs as user `node`.


## Second service: the sample merchant (`noux-demo-merchant`)
A separate web service (same image) that sells two clearly-labelled SAMPLE endpoints (`GET /sample/brief` $0.10, `GET /sample/quote` $0.03)
through the Noux gateway middleware. It is the merchant side of the demo; it needs NO database.

Settings: Language **Docker**, Dockerfile Path `./Dockerfile`, Health Check Path `/healthz`, plan Free, region Frankfurt.
Leave **Docker Command empty**; select the app with the environment variable **`APP=demo-merchant`** (the image's `scripts/start.sh`
runs `apps/$APP`; default `api`). Do not rely on the Docker Command field: its quoting is platform-specific and a quoted
`sh -c "cd ... && ..."` was passed to the shell as one command name and failed with `not found` (status 127).
Name it exactly `noux-demo-merchant` (the directory listing points at `https://noux-demo-merchant.onrender.com`).

Env (generated by `pnpm setup-demo-merchant` into the git-ignored `.env.render.merchant`; paste with "Add from .env"):
`RPC_URL`, `PROGRAM_ID`, `CLUSTER`, `CAMPAIGN`, `MINT`, `MERCHANT_PAYTO`, `GATEWAY_PAYER_B58` (pays rent for sales it opens),
`MERCHANT_SIGNER_B58` (lets it settle right after delivery and refund; omit to leave settlement to the keeper),
`FACILITATOR=cdp` + `CDP_API_KEY_ID` / `CDP_API_KEY_SECRET` (this is the service that talks to the facilitator), `CLAIMS_API_URL`, `PUBLIC_URL`.

Then register its signed listing once the API is deployed: `pnpm setup-demo-merchant --no-env` (idempotent).
Try it end to end with the scripted buyer agent: `pnpm demo-buy`.

## Measured capacity (devnet, 2026-10-28)
`apps/api/scripts/gateway-load.ts` drives the real stack (claim API, gateway, Coinbase CDP facilitator, program, Helius RPC) with concurrent funded buyers. Results on our Helius plan (limits unknown to us):

| Concurrent buyers | All served correctly | Wall time | Slowest purchase |
|---|---|---|---|
| 1 | yes | 8.6 s | 8.6 s |
| 10 | 10/10 | 13 s | 13 s |
| 20 | 20/20 | 20 s | 20 s |
| 30 | 30/30 | 25 s | 25 s |
| 40 | 40/40 | 33 s | 33 s |

- **Correctness held at every size:** nobody paid twice, every 200 matched exactly one payment, every sale settled with the exact split, and one claim sent 30 times at once opened exactly one sale.
- **Throughput is about 1 to 1.5 purchases per second, limited by the RPC plan, not the gateway.** The facilitator is fast (verify about 0.7 s, settle about 1.6 s). Opening the sale is the slow stage (p95 20 s at 30 buyers) because the RPC provider throttles: with 20 concurrent transactions, `getLatestBlockhash` alone took 2.5 s at the median and confirmations 7 s, and web3.js retries HTTP 429 silently (the public devnet RPC refused outright). Each purchase costs about ten RPC calls.
- The merchant's settle-after-delivery takes about 15 s at 30 buyers but runs in the background, so buyers do not wait for it.
- **What to do for more:** a paid RPC plan with higher limits, and watch for 429s. Caching a blockhash and batching confirmations would cut calls further and are not built.
- **100 concurrent buyers (measured on a slow network, about 2 s per round trip, so pessimistic):** 87 of 100 purchases succeeded, with every safety check intact (nobody paid twice, no charge without service, exact splits, no payment left unsettled). Opening sales on-chain was the bottleneck (median 13 s, slowest 38 s), so 80 of the 100 claims hit the 20 s open limit and **failed open**: those buyers paid the merchant in full and the referral was lost. The 13 failures were buyer-side connection errors in the test client. The Coinbase verify step also slowed to about 10 s at the median under that load. This is the cost of an RPC-bound design: it degrades safely, but referrals are the first thing lost. A paid RPC plan with higher limits is the fix.
- Two problems this run exposed, both fixed: (1) the claim service's campaign read made one RPC call per concurrent request whenever its cache expired (now one shared read, and the last good copy is served if the refresh fails); (2) the gateway could answer differently to the unpaid and the paid request for the same claim (the first sale open failed, the retry succeeded), so the buyer's payment, signed for the first payee, was refused. The first answer for a claim now stands until the claim expires, and an open that takes longer than 20 s fails open instead of holding the buyer.
- A note for anyone running load tests from a slow connection: Node gives each address only 250 ms to connect, which fails against hosts with several addresses (Coinbase, x402.org); `NODE_OPTIONS=--network-family-autoselection-attempt-timeout=5000` fixes it.
- **Soak (12 minutes at 0.5 sales per second on devnet, then a drain):** 364 claims through the gateway, all answered correctly, 0 errors, 0 RPC rate-limit retries. Heap stayed flat (36 to 40 MB; 1.3 MB drift between the first and second half), memory rose from 227 to about 310 MB in the first minutes and then plateaued, open handles stayed under 16, event-loop lag peaked at 105 ms. The keeper closed all 364 unpaid sales (slowest tick 19 s), and every lamport of rent came back (net cost 0.005 SOL, fees only). The gateway's per-sale memory (one entry per claim, capped at 10,000) is the only state that grows.
- **Soak with real purchases, and a backlog of funded sales (devnet, real Coinbase facilitator, real USDC):** two runs. First: 60 purchases spread over 10 minutes plus a 60-purchase burst through a gateway that does not settle: 119 of 120 served, all 119 settled with exact splits, memory flat (heap 42 MB, no drift), event-loop lag peak 326 ms; one purchase was refused with a bare 402 (the buyer was not charged) and the gateway could not say why, so failure events were added (`payment_invalid`, `payment_verify_failed`, `payment_settle_failed`). Second run, 40 spread over 6 minutes plus a 40-sale backlog: **80 of 80 served, 6 of 6 checks held** (nobody paid twice, every 200 matched one payment, exact splits, nothing left holding a payment unsettled), no refusals. **The keeper settled all 40 funded sales in its second tick** (the first tick correctly waited out the full hold; settling 40 took about 29 s) and the first run's 60 in about 44 s. The hosted keeper on Render also watches these sales, so some settlements may have been won by it; the chain shows every sale settled once.
- **The unexplained 402, explained and fixed.** In about 1% of real purchases (2 of about 220) the Coinbase facilitator answered `settlement_pending: transaction did not confirm in time: context deadline exceeded`: it had submitted the payment but not seen it confirm before its own deadline. That answer means "unknown", not "refused" (the payment can still land, which would charge the buyer and show a 402). The gateway now treats it as ambiguous: it checks the chain, counts the payment as settled if it landed, resubmits the identical signed payment once if it is confirmed absent, and surfaces the error without guessing if the chain cannot be read. Verified by unit tests with the facilitator's exact wording (both as a returned failure and a thrown error); a confirmation run of 100 real purchases passed 100/100 with every buyer charged exactly once, but the timeout did not recur in that run, so the fix has not been seen working live. In both observed cases the refused buyer was not charged.
- A single purchase takes about 11 to 14 seconds end to end on this devnet setup under this load (claim, sale open, facilitator verify and settle, buyer's own RPC calls), most of it RPC round trips.
- Not measured: mainnet, and anything above about 100 simultaneous buyers.

## Measured capacity: indexer and public API (synthetic data, 2026-10-28)
`apps/api/scripts/indexer-scale.ts` runs the real `syncOnce` and the real HTTP routes over a real Postgres, with synthetic snapshots (no chain, local Postgres with almost no network delay, so a hosted database will be somewhat slower). Before and after rewriting the sync:

| Sales indexed | One sync with no changes, before | After | First full sync, after |
|---|---|---|---|
| 1,000 | 0.9 s | 0.1 s | 0.25 s |
| 5,000 | 7.2 s | 0.13 s | 0.7 s |
| 20,000 | 16.9 s | 0.24 s | 1.9 s |
| 50,000 | not run | 0.6 to 1.8 s | 4 to 9 s |

- The old sync rewrote every sale one row at a time on every pass. Finished sales never change on-chain, so only new and open sales are written now, in batches of 500.
- API latency (campaign list, stats, receipts, one distributor, one campaign's sales) stayed under about 200 ms at 50,000 sales; one 4.6 s campaign-list reading at 50,000 did not reproduce in two reruns (probably stale planner statistics right after a bulk load).
- The explorer links (open, payment, settlement) are filled in the background, 30 sales per sync, newest first, with exponential backoff for sales that cannot be read. A new index of 5,000 old sales takes about 3 hours to link them all; 20,000 takes about 11 hours. Sales without links still show their numbers.
- **Incremental sync (default, `INDEXER_MODE=incremental`).** A full snapshot downloads every Sale account (about 246 bytes each: 1.2 MB at 5,000 sales, 12 MB at 50,000) every pass, which is the real RPC limit at scale. The indexer now follows the chain by deltas: new program transactions since a cursor, then only the Sale accounts those transactions carried plus every sale the database still has open (a payment into a vault is a plain token transfer, not a program transaction, so open sales are always refreshed). Campaigns are re-read each pass (few and small). A quiet pass costs one signature query, one campaign read and one batch read for the open sales; nothing else. Safety nets: the cursor lags 90 s so a transaction a node indexes late is re-read; a full snapshot runs at start, every 6 hours, and whenever the delta fails or is too large (over 3,000 new transactions); `INDEXER_MODE=full` turns the delta path off. `/v1/index` reports `lastMode` and `lastFullSyncAt`.
- **Verified:** a randomized equivalence test (6 seeds x 40 steps, plus 3 seeds with transactions indexed late) requires identical tables to a full snapshot after every step; five deliberate bugs (open sales not refreshed, transactions ignored, no cursor lag, closed sales never removed, ...) are each caught. On real devnet, after real activity (open, pay, settle, refund), the incremental database matched a fresh full snapshot exactly (270 sales, 64 campaigns, 0 differing rows).
- **Limits:** a sale changed only by a call from another program (a CPI) is invisible to the delta path until the next full snapshot (at most 6 hours); the campaign read still scales with the number of campaigns; the keeper reads vault balances 100 per RPC call and works through a backlog six transactions at a time (120 expired sales: 485 s sequentially, about 100 s now, on devnet).

## RPC usage and free hours
- The indexer (every 60 s) and the keeper (every 30 s) use `getProgramAccounts`, the heaviest kind of RPC call. Check your RPC plan's
  usage dashboard; tune `INDEXER_INTERVAL_SECONDS` / `KEEPER_TICK_SECONDS`, or set `ENABLE_INDEXER=0`.
- Render's 750 free hours/month are shared by the whole workspace. A service that is kept awake 24/7 uses ~744 h, so two
  always-awake free services will exhaust the month. Keep pings for the judging window only, or pay for one service.

## Website (apps/web) on Vercel
Static Vite site; no secrets. Import the GitHub repo in Vercel, Root Directory `apps/web`, add env `ENABLE_EXPERIMENTAL_COREPACK=1`. `apps/web/vercel.json` holds the install/build commands and the single-page-app rewrite. Optional env: `VITE_API_URL` (defaults to the live API), `VITE_RPC_URL` (defaults to the public devnet node; never put a keyed RPC URL here, it is shipped to every browser).
